# ADR: Layered Thinking Block Handling

**Date:** 2026-03-29
**Status:** Accepted
**Issue:** #4 — MiniMax 400: portable transformation strips thinking blocks required by multi-turn tool calls

## Context

ModelProxy's portable transformation strips ALL thinking blocks from both request and response directions. This causes Anthropic-compatible third-party vendors (MiniMax, Qwen) to fail on multi-turn tool call conversations because they require complete conversation history including thinking blocks.

However, Anthropic's API requires thinking blocks to have valid cryptographic signatures. Sending unsigned thinking blocks (from third-party vendors) to Anthropic causes server-side signature validation failure.

These two requirements are in direct conflict:
- Third-party vendors need thinking blocks preserved
- Anthropic rejects unsigned thinking blocks

## Research Findings

### Anthropic API Thinking Block Rules

Source: https://platform.claude.com/docs/en/docs/build-with-claude/extended-thinking

| Rule | Detail |
|------|--------|
| Signature required for server | "The server decrypts the `signature` to reconstruct the original thinking for prompt construction" |
| Thinking blocks can be omitted entirely | "While you can omit `thinking` blocks from prior assistant role turns" — allowed but loses reasoning continuity |
| Cannot send unsigned thinking | Sending thinking blocks without valid Anthropic signatures causes the server to fail signature decryption |
| Must not modify thinking blocks | "The entire sequence of consecutive thinking blocks must match the outputs generated by the model during the original request; you can't rearrange or modify the sequence of these blocks" |
| Client SDK does NOT validate signatures | SDKs treat thinking blocks as opaque data; no client-side signature validation on responses |

### MiniMax Anthropic API Compatibility

Source: https://platform.minimaxi.com — Anthropic API Compatibility docs

| Aspect | Detail |
|--------|--------|
| `thinking` parameter | Fully supported |
| `type="thinking"` in messages | Fully supported |
| Multi-turn tool call requirement | "必须将完整的模型返回（即 assistant 消息）添加到对话历史，以保持思维链的连续性" — complete assistant messages including thinking must be preserved |
| Supported models | MiniMax-M2.7, M2.5, M2.1, M2 and their highspeed variants |

### Cross-Vendor Failure Scenario (Previously Observed)

Reproduced by user in a prior session:

```
1. Main session: Opus → Anthropic (transparent, thinking blocks with valid signatures)
2. /commit skill: Haiku → Qwen3.5 via proxy (portableOnly)
3. Qwen3.5 returns thinking blocks WITHOUT Anthropic signatures
4. If thinking blocks not stripped: client stores them
5. Main session resumes: Opus → Anthropic (transparent, no body modification)
6. Anthropic receives Qwen3.5's unsigned thinking blocks
7. Server attempts signature decryption → fails → error
```

This failure motivated the original implementation of `isNonPortableBlock()` stripping all thinking blocks.

### Same-Vendor Failure Scenario (Issue #4)

Reproduced in current session (WebSearch tool returned MiniMax 400):

```
1. Claude Code sends request through proxy → MiniMax
2. MiniMax returns response with thinking + tool_use blocks
3. Proxy strips thinking from response (portable normalization)
4. Client receives assistant message without thinking
5. Client sends next request with incomplete assistant message
6. MiniMax: 400 "invalid params, function name or parameters is empty (2013)"
```

The proxy's branch system stores full messages (with thinking) per vendor and should provide them for same-vendor requests via hash-based prefix matching. However, the response-side stripping means the client never has thinking blocks to include in subsequent requests, creating a dependency on branch matching that fails on cold starts and cache misses.

## Decision

### Approach: Layered Thinking Block Handling

Instead of a binary "strip all" or "keep all" approach, implement vendor-aware layered handling:

| Direction | Route Type | Handling |
|-----------|-----------|----------|
| Response → client | Third-party (.portableOnly) | Keep thinking content, strip `signature` field |
| Request → third-party | .portableOnly | Keep thinking content, strip `signature` field |
| Request → Anthropic | .transparent (new guard) | Strip UNSIGNED thinking blocks (no `signature` field) |
| Response → client | Anthropic (.transparent) | Pass through unchanged |

### Key Insight

The `signature` field is the discriminator:
- **Blocks with `signature`** = Anthropic-signed, required by Anthropic, safe to pass to third parties (they'll ignore the signature)
- **Blocks without `signature`** = from third-party vendors, needed by those vendors, must NOT reach Anthropic

### Changes

1. `TranscriptProjector.isNonPortableBlock()` — narrow to only `redacted_thinking`
2. `PortableContentNormalizer` SSE — forward thinking events, suppress only `signature_delta`
3. `ProxyForwarder` — add `stripUnsignedThinkingBlocks()` guard for Anthropic-bound requests

### Scenario Verification

| Scenario | Before | After |
|----------|--------|-------|
| MiniMax → MiniMax (multi-turn tool call) | 400: thinking stripped | Thinking preserved, complete history |
| Qwen3.5 → Anthropic (cross-vendor) | Unsigned thinking leaked → signature error | Unsigned thinking stripped at Anthropic boundary |
| Anthropic → MiniMax | Thinking stripped entirely | Thinking content forwarded (signature stripped) |
| /commit (Haiku→Qwen3.5) → Opus | Unsigned thinking leaked → error | Unsigned thinking stripped at Anthropic boundary |
| Web Search via third-party | 0 results (multi-turn tool call broken) | Tool call chain preserved |

## Alternatives Considered

### A. Change replay policy to `.transparent` for all third-party vendors

Pros: Simplest change (one-line config)
Cons: Disables branch tracking and replay deduplication for third-party vendors. Also leaks unsigned thinking to Anthropic in cross-vendor scenarios.

### B. Keep current stripping, rely on branch system for same-vendor continuity

Pros: No code changes needed
Cons: Branch system only works when hash matching succeeds. Cold starts, cache misses, and long conversations may break. The response-side stripping means clients never store thinking, creating an unreliable dependency chain.

### C. Add vendor-level `preserveThinkingBlocks` flag

Pros: Per-vendor granularity
Cons: Requires user configuration for each vendor. Doesn't solve the cross-vendor contamination problem. Users would need to understand the technical implications.

### D. Replace stripped thinking blocks with empty markers

Pros: Maintains message structure
Cons: Hacky. Third-party vendors may not accept empty thinking blocks. Doesn't preserve reasoning continuity.
